บอร์ดที่ติดตั้งไว้ไกลตัวย่อมหลุด Wi-Fi สักวัน ไม่ว่าจะเพราะเราเตอร์รีสตาร์ต ไฟตก หรือสัญญาณ
รบกวน โค้ดมาตรฐาน `while (WiFi.status() != WL_CONNECTED) delay(500);` ผ่านการต่อครั้งแรก
ไปได้ แต่จะทำให้ทั้งบอร์ดค้างทันทีที่สัญญาณหลุดครั้งแรก

## ทำไมลูปแบบหยุดรอถึงใช้ไม่ได้

`delay()` หยุด `loop()` ทั้งหมด ระหว่างที่บอร์ดรอ Wi-Fi มันไม่อ่านเซนเซอร์ ไม่เคลียร์วอตช์ด็อก
และไม่ตอบคำขอใด ๆ เราเตอร์ดับห้านาที จึงกลายเป็นเซนเซอร์ดับห้านาทีตามไปด้วย

## เปลี่ยนเป็นตรวจตามรอบเวลาแทน

ตัวอย่างต่อไปนี้เป็นส่วนของเฟิร์มแวร์บนบอร์ดจริง ไม่ใช่โค้ดครบไฟล์
ต้องเพิ่ม `WiFi.h`, การตั้งค่าเริ่มต้น, `ssid`, `password`, `readSensors()` และ `publish()`
ให้ตรงกับโปรเจกต์ก่อนคอมไพล์ การจำลองในหน้าเว็บไม่ยืนยันการเชื่อมต่อ Wi-Fi จริง

ให้การตรวจสอบการเชื่อมต่ออยู่ใน `loop()` แล้วคุมด้วยเวลาที่ผ่านไป งานอ่านเซนเซอร์จะได้ทำงาน
ทุกรอบไม่ว่าสถานะเครือข่ายจะเป็นอย่างไร

```cpp
const unsigned long RETRY_MS = 5000;
unsigned long lastAttempt = 0;

void loop() {
  readSensors();

  if (WiFi.status() == WL_CONNECTED) {
    publish();
    return;
  }

  if (millis() - lastAttempt >= RETRY_MS) {
    lastAttempt = millis();
    WiFi.disconnect();
    WiFi.begin(ssid, password);
  }
}
```

การลบค่า `millis()` แบบนี้ยังถูกต้องแม้ตัวนับจะวนกลับหลังราว 49 วัน เพราะทั้งสองฝั่งเป็นชนิด
ไม่มีเครื่องหมาย แต่การเขียน `millis() > next` จะพังตอนวนกลับ

## ต้องเรียก disconnect ก่อน begin

การเรียก `WiFi.begin` ซ้ำบนการเชื่อมต่อที่ค้างครึ่งทาง มักไปใช้สถานะเดิมที่เสียแล้วและไม่มีทาง
สำเร็จ การเรียก `WiFi.disconnect()` ก่อนจึงบังคับให้เริ่มเชื่อมต่อใหม่จริง ๆ

## ข้อมูลที่ส่งไม่ได้ต้องตัดสินใจว่าจะทำอย่างไร

ระหว่างที่เครือข่ายหลุด `publish()` ไม่ถูกเรียกเลย ต้องตัดสินใจให้ชัดว่าค่าที่อ่านได้ช่วงนั้นจะทิ้ง
หรือเก็บไว้ ปกติแล้วบัฟเฟอร์วนขนาดคงที่คือคำตอบที่ถูก เพราะคิวที่โตได้ไม่จำกัดจะกินหน่วยความจำ
จนบอร์ดรีสตาร์ตกลางคันพอดี

## อย่าลองใหม่ถี่เกินกว่าที่วงจรวิทยุจะไหว

ระยะเวลาลองใหม่ที่สั้นกว่าราวสองวินาที ทำให้การเชื่อมต่อยังไม่ทันเสร็จก็ถูกยกเลิกด้วยรอบถัดไป
ผลคือบอร์ดไม่มีวันต่อสำเร็จเลย ห้าวินาทีคือค่าต่ำสุดที่ปลอดภัย
